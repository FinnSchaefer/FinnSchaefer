The model is not the system

Machine learning is, at its core, a way of fitting parameterized functions to data. Much of modern deep learning still runs on repeated linear maps, high-dimensional geometry, and gradient-based optimization. What people now call AI is usually larger than the model: retrieval, tools, memory, policy layers, and automation wrapped around ML. That distinction matters in security because the failure is often not that a component crashes, but that a bad input is accepted as normal.

Introduction

During my internship at the U.S. Government Accountability Office, I spent time evaluating AI claims in cybersecurity products. More recently, I began reading Why Machines Learn, which is useful for exactly the reason a hype cycle is not. It keeps pulling the conversation back to geometry, approximation, optimization, and the unglamorous but decisive role of linear algebra.

That perspective aligns with the rest of my work. I focus on systems in which assumptions about authenticity, integrity, and provenance shape behavior, particularly when those assumptions fail quietly and the failure still appears valid to the system consuming it. From that baseline, the current AI conversation becomes easier to parse. Much of the underlying machinery remains machine learning. What has changed is how those learned functions are deployed: embedded within larger decision systems that retrieve external context, call tools, maintain state, cross trust boundaries, and, in some cases, act.

So the argument here is simple. Machine learning is mostly about fitting a function. Today's AI is usually a system built around that fitted function. The difference sounds semantic until you try to secure it.

The short version

The cleanest technical description of machine learning is still empirical risk minimization:

\[ \hat{\theta} = \arg\min_{\theta} \frac{1}{n}\sum_{i=1}^{n} \ell\big(f_{\theta}(x_i), y_i\big) \]

Given examples \((x_i, y_i)\), choose parameters \(\theta\) so that the learned function \(f_{\theta}\) minimizes some loss \(\ell\). Different model families change the parameterization, the inductive bias, and the optimization landscape, but the basic story does not move very much from Rosenblatt's perceptron to modern deep networks.

What changed in the current wave is not that ML disappeared. It is that the fitted function got scaled, instruction-tuned, and embedded in a larger system. NIST's AI RMF and its generative-AI profile both frame the operational object as an AI system with actors, interfaces, lifecycle risks, and effects on real or virtual environments, not merely as an isolated model. In practice, that system may include retrieval, external memory, policy layers, tool use, and automated action.

Why machine learning really works

The first thing worth saying out loud is that most of the numerical work is linear. The perceptron already had the essential geometry:

\[ \hat{y} = \operatorname{sign}(w^{\top}x + b) \]

a hyperplane slicing a feature space into decisions. Modern networks are more expressive, but the computational body is still mostly repeated affine maps with simple nonlinearities:

\[ h_{\ell + 1} = \sigma(W_{\ell} h_{\ell} + b_{\ell}) \]

Universal approximation results explain why such compositions can represent very rich function classes. Backpropagation explains how to fit them efficiently enough to matter in practice. What we call depth is, in large part, the repeated application of linear maps, punctuated by nonlinearities that keep the whole construction from collapsing into a single matrix.

Even transformers, which feel qualitatively different when used as language systems, still rely on learned linear projections into query, key, and value spaces:

\[ \operatorname{Attn}(Q, K, V) = \operatorname{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d}}\right)V \]

The architecture is novel and powerful, but the numerical work is still projection, weighting, and aggregation at scale. The same point also shows up in fragility. The classic adversarial-example result from Goodfellow, Shlens, and Szegedy argued that vulnerability can emerge from effective linearity in high-dimensional spaces, not from some mystical nonlinear failure mode.

The language-model era follows the same template. The training objective is not hidden inside philosophy. It is next-token prediction, usually written as cross-entropy over long sequences:

\[ \mathcal{L}(\theta) = -\sum_t \log p_{\theta}(x_t \mid x_{< t}) \]

Scale changed what that simple objective could buy. GPT-3 showed much stronger few-shot performance than earlier systems, and empirical scaling-law work made clear that model performance improved predictably with more parameters, data, and compute. Chinchilla then tightened the picture by showing how model size and token count should be balanced more carefully under a fixed compute budget.

Why AI is not the same thing as ML

If machine learning is the learned function, current AI is usually the learned function plus the rest of the stack. Part of that stack is still inside the model. Instruction tuning and reinforcement learning from human feedback reshape the interface between model and user so that the system follows natural-language intent more reliably than a raw next-token predictor would. Part of it is outside the model. Retrieval-augmented generation gives the model access to external, updatable memory. Tool-use work such as Toolformer and ReAct pushes the system beyond passive prediction and toward selective API calling, planning, and action.

A compact way to write the distinction is

\[ y_{\mathrm{sys}} = \mathcal{O}\big(M_{\theta}(x, r(x), h), \mathcal{T}, \mathcal{P}\big) \]

where \(M_{\theta}\) is the underlying learned model, \(r(x)\) is retrieved context, \(h\) is interaction history, \(\mathcal{T}\) is the set of available tools, and \(\mathcal{P}\) is the policy and permission layer that determines what the system is allowed to do. Classical ML often stops at \(M_{\theta}(x)\). Modern AI products usually do not.

There is also a subtler reason the distinction matters. Some of the most interesting capabilities of large models may look less like static prediction and more like temporary learning inside the forward pass. In stylized linear settings, researchers have shown that transformers can implement procedures resembling gradient descent, ridge regression, and related estimators in context. But the stronger claim that pretrained language models in the wild literally reduce to gradient descent during in-context learning remains unsettled, and recent work argues that the equivalence should not be overstated.

One concrete version of this distinction became clear during my internship at the GAO, where I reviewed commercial cybersecurity offerings and kept returning to a question that marketing material tends to blur: where is the learning actually happening, and where is the rest just engineering wrapped around it? In a platform like Microsoft Purview, some capabilities do rely on learned components, most clearly its trainable classifiers, but much of the operational value still comes from automated pattern matching, labeling, and policy enforcement inside a much broader data security and compliance stack. By contrast, systems closer to CrowdStrike Charlotte AI are better understood as models embedded in a larger operational pipeline: CrowdStrike describes Charlotte AI as combining model-driven triage, contextual enrichment from platform data, and agentic workflows that can recommend or execute response actions under human oversight or predefined logic. That distinction mattered more to me than whether the product brochure called all of it AI, because the security question was never just whether a model was present; it was where learning ended, where workflow began, and where the system acquired the authority to act.

Why the distinction matters in cybersecurity

In cybersecurity, and especially in cyber-physical security, the most interesting failures are often not visible as failures at all. They are accepted states. That pattern is old. In power systems, false-data-injection attacks showed that an adversary could manipulate measurements in ways that evade ordinary bad-data detection while still steering the state estimator. In control systems more broadly, the secure-control literature emphasized that cyber-physical attacks matter precisely because the plant can continue operating while the controller is working from corrupted premises.

Modern AI systems recreate this problem in a different medium. Prompt injection works because language-model-based applications blur the line between data and instructions. In indirect prompt injection, the hostile string does not arrive through a privileged administrator console. It can arrive through content the system retrieves and treats as context, after which the model may reinterpret that context as control. The analogy to trusted-data failures in cyber-physical systems is not perfect, but it is close enough to be operationally useful. In both cases, the system behaves consistently with the trust assumptions we handed it.

This is why the distinction between ML and AI is not semantic in security work. A standalone model that produces a score is one threat surface. A model embedded in a retrieval pipeline, allowed to call tools, connected to privileged data, and used to trigger downstream actions is a different threat surface entirely. NIST's AI RMF, the generative-AI profile, and NIST's adversarial-ML taxonomy all point toward the same conclusion: the real unit of analysis is the full system lifecycle, including interfaces, dependencies, attacker goals, deployment conditions, and post-deployment monitoring.

That framing also fits practical cryptography better than the looser public conversation does. Cryptography gives us authenticity, integrity, authorization, and sometimes provenance. Those are essential properties. They are not the same thing as truth. A signed sensor reading can still be strategically misleading if the sensor is measuring the wrong thing, positioned incorrectly, or compromised upstream. An authenticated document retrieved by an agent can still contain hostile instructions. In other words, the cryptographic question, "Can I trust the source and integrity of this input?", remains necessary, but the AI question adds another layer: "What behavior does this system produce when that input is formally valid and semantically dangerous?"

What matters operationally

The practical lesson I took from reviewing vendor claims is that the label matters less than the trust map. If a product is doing supervised learning on labeled telemetry to rank alerts, then I want to know the feature pipeline, the training distribution, the false-positive and false-negative tradeoffs, the retraining cadence, and the adversarial assumptions. That is an ML evaluation.

If a product is built on a foundation model with retrieval, a conversational interface, and workflow automation, then I also want to know what it can read, what it can write, what tools it can call, how retrieved content is separated from control instructions, what authority boundaries constrain it, and how failures are logged and reversed. That is an AI-system evaluation.

For my part of the security world, the highest-value questions are usually the least theatrical ones. Which inputs are treated as trusted? Which assumptions are backed by cryptographic verification, and which are merely organizational wishes? Where can external data become internal control? What happens when the model is confidently wrong? In cyber-physical environments, do not ask only whether the model is accurate on average. Ask whether the actuation path is constrained when the input stream is valid-looking but adversarial. In enterprise security, do not ask only whether the copilot is helpful. Ask whether retrieved text can steer tool calls or exfiltrate data.

That is why I have become skeptical of the lazy dichotomy between "real AI" and "hype." The more useful distinction is between systems whose behavior is legible in terms of prediction and systems whose behavior is amplified by memory, retrieval, tools, and permissions. The former can still be dangerous. The latter can fail in more ways because they have more ways to touch the world.

Conclusion

Machine learning is not a mystical category. It is a family of methods for fitting parameterized functions under data, compute, and optimization constraints. Much of modern deep learning still runs on linear maps, vector geometry, and gradient descent, even when the resulting behavior looks qualitatively new at the interface.

But the current AI wave is not just ML with better branding. It is ML embedded in systems with memory, retrieval, tools, policy layers, and action surfaces. That is what I kept seeing while sorting cybersecurity products, and it is what continues to matter in my own work. If you care about cyber-physical security, trusted data, practical cryptography, and applied security engineering, the lesson is straightforward: do not stop at the model. Find the trust boundary. Find the action boundary. Find the place where a bad input can still look normal.

The model is learned. The system is engineered. The risk lives at their boundary.
